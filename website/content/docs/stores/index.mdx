A **state store** persists workflow runs and step checkpoints — the source of truth for both
durability and the [dashboard](/docs/observability/dashboard). It's a pluggable `StateStore`
interface, independent of the [transport](/docs/transports).

<Callout>
  Writing a **custom store?** The interface includes `renewRunLock(runId, owner, leaseUntilMs)` (for
  [lease renewal](/docs/concepts/durability#deploys-versioning--multiple-instances) while a run executes)
  and `listPendingRuns(limit)` (so workers can poll for [`pending`](/docs/concepts/durability#the-execution-model-start-enqueues-a-worker-runs-the-body)
  runs to dispatch). All bundled adapters implement both.

  It also declares **`runFacets(query)`** — `(status, origin)` counts, which is what lets the
  [console](/docs/observability/dashboard#counting-without-listing) page its run list while its chips
  keep reporting the whole set. That one is **optional**: a store that omits it still works, with the
  caller falling back to counting a full listing. Every bundled adapter pushes it down to a
  `GROUP BY`, and `RunQuery.origin` accepts `null` there and in `listRuns` to select the runs carrying
  no origin at all.

  **`runValueFacets(axis, query, opts?)`** is optional in the same way: the distinct VALUES of one
  filter axis with counts, which is what lets a console offer a picker instead of a text box. A store
  that omits it leaves those controls as free text. Every bundled adapter answers the run-table axes
  with a `GROUP BY`; `tag` and the search-attribute axes are counted over a bounded scan, since their
  values live outside the row being counted.
</Callout>

## Writing a custom store: the fan and hot-path methods

Several `StateStore` methods exist only to keep wide fans and busy deployments cheap. All but one are
optional, and the engine falls back to something slower but correct when a store leaves one out.
Run the [shared store contract](/docs/testing#testing-a-custom-storetransportadmission-backend)
(`runStateStoreContract`) against your adapter. Its `listDueTimers` case checks the ordering and
the `limit`. Its cases for `countCheckpoints`, `saveCheckpointIfPending`, `saveCheckpointsIfPending`,
`registerChildWaits`, `listCheckpointsByNamePrefix`, `checkpointStats` and `queryCheckpoints` expect the method to exist, because every bundled adapter has it: a
custom store that leaves one out fails those cases even though the engine would fall back.

| Method | Required? | What the engine uses it for | Without it |
| --- | --- | --- | --- |
| `listDueTimers(nowMs, namespace?, limit?)` | required; honoring `limit` is optional | the due-timer pass. Return the most overdue first (`wakeAt` ascending), at most `limit` runs. The engine passes its `timerBatchSize` (default 500). | A store that ignores `limit` still works; every instance then loads the whole due set on each tick. |
| `countCheckpoints(runId, fromSeq, toSeq, statuses)` | optional | a step fan's join barrier asks, once per batch of results, how many checkpoints in the fan's seq range are still `pending`. Must be a `COUNT`, not a load. An empty `statuses` counts 0. | The engine loads the run's checkpoints and counts in memory, once per batch of results. |
| `saveCheckpointIfPending(checkpoint)` | optional | a compare-and-set: overwrite `(runId, seq)` only while the stored row is still `pending`, and resolve whether it wrote. Used to settle a step from its result (which also drops a duplicate delivery), to stamp a redispatch deadline, and to re-dispatch. | The engine uses `saveCheckpoint`, which keeps the race where a turn writes a settled step back to `pending` and the step runs twice. |
| `saveCheckpointsIfPending(checkpoints)` | optional | `saveCheckpointIfPending` for many rows in one call, resolving one boolean per entry in input order. It must give the same answers as calling `saveCheckpointIfPending` on each entry in turn: a second entry for the same row is compared against the first one's write. Each row's compare-and-set stays atomic, and so does the call: if it rejects, it wrote nothing. The engine settles a batch of one run's step results with one call. | One `saveCheckpointIfPending` per result. |
| `hasSignalWaiter(runId, tokenPrefix)` | optional | a child fan's join barrier. | The parent replays once per settled child, which is O(N²) over the fan. |
| `registerChildWaits(entries)` | optional | writes a child fan's waiters and `running` placeholders in one transaction, 500 at a time. | Waiters and placeholders are written one by one. |
| `compactCheckpoints(runId, fromSeq, toSeq, into)` | optional | folds a settled child fan (or wave) of 100+ into one `fan:` checkpoint. | Settled fans keep one checkpoint per child. |
| `listCheckpointsByNamePrefix(runId, prefixes)` | optional | reads a fan's existing checkpoints in one prefix query. | `listCheckpoints` plus a prefix filter in memory. |
| `listSignalWaitersByRun(runIds)` | optional | run-scoped waiter reads (run detail, cancel, purge, the timer pass). | Those reads scan every waiter. |
| `checkpointStats(runId, { group? })` | optional, paired with `queryCheckpoints` | the console's summarized run detail and fan pages, and their ETag. One `GROUP BY parallel_group, status, <name kind>` returning a `CheckpointStat` per bucket: count, seq and name bounds, earliest `enqueuedAt` (read as `startedAt` when null), start and finish bounds, attempt sum. The name kind is `child` (`signal:child:`), `folded` (`fan:`), `spawn` (`spawn:`) or `step`. | `StoreRunGateway` reads every checkpoint of the run and summarizes in memory, on every poll. A 40,000-member fan is a full read each time. |
| `queryCheckpoints(runId, { group?, excludeGroups?, statuses?, namePrefixes?, offset?, limit? })` | optional, paired with `checkpointStats` | the rows the summary still needs (those outside wide fans, folded checkpoints, a fan's first 20 failures, the first child edges) and one page of a fan's members. Seq order. `excludeGroups` keeps ungrouped rows. An empty `statuses` or `namePrefixes` matches nothing. | Same as above: one full read per detail and per page. |

Every bundled adapter (MikroORM, TypeORM, Prisma, Drizzle on SQLite/MySQL and on Postgres, and the
in-memory store) implements `listDueTimers` with `limit` and ordering and every optional method in the
table. `saveCheckpointIfPending` is a single conditional `UPDATE … WHERE status = 'pending'` in each,
never a read followed by a write, and `countCheckpoints` is one `COUNT(*)` over the run's seq range.
`saveCheckpointsIfPending` is one `UPDATE … FROM (VALUES …) WHERE status = 'pending' RETURNING` per
500 rows on Drizzle Postgres, and those same conditional `UPDATE`s, one per row, in one transaction
on the other stores. It is one commit per batch either way.

`checkpointStats` is one aggregate query. Each SQL store also declares a
`durable_step_checkpoints_group_idx` index on `(run_id, parallel_group, seq)` for the per-fan reads.
MikroORM and TypeORM add it on boot, Drizzle Postgres's `DURABLE_PG_DDL` creates it `IF NOT EXISTS`,
and Prisma and Drizzle SQLite get it from your next migration.

Two things the store must not try to do in SQL: decide whether a child failed, or count the children
a folded checkpoint stands for. Both live in the payload (`{ ok: false }`, `output.values`), which a
`CodecStateStore` may have encrypted. Core loads those rows through `queryCheckpoints` and reads them
after decoding. On a collation that ignores case (MySQL's default), the name kind and the
`namePrefixes` match ignore case too. Engine-written names are lower-case, so in practice only a step
you named something like `FAN:x` would be affected.

`CodecStateStore` exposes an optional method only when the store it wraps has it, so wrapping a
store never hides a capability or invents one. It encodes the payload for `saveCheckpointIfPending`
and for every entry of `saveCheckpointsIfPending`, forwards `countCheckpoints` and `checkpointStats`
verbatim (neither reads a payload), decodes the rows `queryCheckpoints` returns, and decodes the runs
`listDueTimers` returns.

## Adapters

Each adapter has its own page with the full setup — register/copy the schema, wire the store, and
own migrations:

| Store | Database | Schema | |
| --- | --- | --- | --- |
| `InMemoryStateStore` (in core) | — | — | For tests and local dev. Not durable. |
| [MikroORM](/docs/stores/mikro-orm) | Postgres · MySQL · SQLite | auto-schema or `ensure*` | The reference adapter. |
| [TypeORM](/docs/stores/typeorm) | Postgres · MySQL/MariaDB · SQLite | auto-schema or `ensure*` | Register `ENTITIES` on your `DataSource`. |
| [Prisma](/docs/stores/prisma) | any Prisma datasource | Prisma Migrate | Add the models, `prisma generate`, pass your `PrismaClient`. |
| [Drizzle](/docs/stores/drizzle) | SQLite / libSQL (Turso, edge) | drizzle-kit | Build your db with the package's schema. |
| [Drizzle (Postgres)](/docs/stores/drizzle-postgres) | PostgreSQL | drizzle-kit or auto-schema | `@dudousxd/nestjs-durable-store-drizzle/pg` — any drizzle Postgres driver. |

The MikroORM and TypeORM adapters work on any SQL database their ORM supports — **Postgres, MySQL or
SQLite** (timestamps use native datetime columns, so epoch values never overflow). The quickest wire
is one factory:

```ts
import { MikroOrmStateStore } from '@dudousxd/nestjs-durable-store-mikro-orm';

DurableModule.forRootAsync({
  inject: [MikroORM],
  useFactory: (orm) => ({ store: new MikroOrmStateStore(orm), transport }),
});
```

## Auto-schema

For the **MikroORM**, **TypeORM** and **Drizzle (Postgres)** adapters, the module creates the durable tables on boot
(`durable_workflow_runs`, `durable_step_checkpoints`, `durable_run_attributes`,
`durable_signal_waiters`, `durable_buffered_signals`) — zero setup in dev. Turn it off in production
and own the schema via a migration:

```ts
DurableModule.forRoot({ store, autoSchema: false });
```

Each of those adapters exports the exact function to call from your own migration —
`ensureMikroOrmDurableSchema(orm)`, `ensureTypeOrmDurableSchema(dataSource)` and
`ensureDrizzlePgDurableSchema(db)` (whose SQL is also exported as `DURABLE_PG_DDL`). See the
[MikroORM](/docs/stores/mikro-orm#schema-auto-on-boot-or-your-own-migration) and
[TypeORM](/docs/stores/typeorm#schema-auto-on-boot-or-your-own-migration) pages for the full
migration snippets. It only ever adds the durable tables — it never touches yours.

The **Prisma** and **Drizzle (SQLite)** adapters have no auto-schema: their ORMs already own your
schema and migration history, so you create the durable tables with `prisma migrate` / `drizzle-kit`
(the `autoSchema` option is a no-op for them). The Drizzle Postgres store supports both: re-export its
`pgTable`s into your drizzle-kit schema, or let auto-schema create the identical tables.

## Column naming

All four adapters agree on physical column names for the `durable_*` tables so a run written by one
is readable by another. The MikroORM and TypeORM adapters expose this as an explicit choice —
`durableEntities({ naming })` — rather than leaving it to the host ORM's naming strategy, which is
what silently diverged the adapters in the past:

```ts
import { durableEntities } from '@dudousxd/nestjs-durable-store-mikro-orm'; // or -typeorm

entities: durableEntities({ naming: 'snake_case' }); // default; or 'preserve', or a (property) => string fn
```

`'snake_case'` is the default and canonical (matched by the Prisma and Drizzle schemas too).
`'preserve'` keeps the camelCase property name verbatim — only for reading a table an old,
unpinned TypeORM/Prisma adapter produced. See the [MikroORM](/docs/stores/mikro-orm#column-naming)
and [TypeORM](/docs/stores/typeorm#column-naming) pages for the full signature.

## Exactly-once DB writes with `ctx.transaction`

A plain `ctx.step` is at-least-once: if the process dies after the step's business write commits but
before its checkpoint does, the step re-runs on replay. `ctx.transaction(name, fn)` closes that gap by
writing the business row **and** the checkpoint in the same store transaction, so they commit or fail
together:

```ts
await ctx.transaction('create-order', async (tx) => {
  await this.orders.insert(tx, { id: orderId, total }); // your write, on the store-native tx handle
  // checkpoint commits atomically with the write above — never done-but-unrecorded
});
```

`fn` receives the store-native transaction handle (a TypeORM/MikroORM `EntityManager`, a Prisma tx
client, or a Drizzle tx) — run your own writes on it, not on your app's regular connection. Needs a
SQL store that implements `transaction()` (all four bundled adapters do); throws on a store that
doesn't.

## Encrypting payloads

`CodecStateStore` wraps ANY store and runs run/step **payloads** (`input`/`output`) through a
`PayloadCodec` — encoded on write, decoded on read — so they're never persisted in the clear. Metadata
the dashboard and queries need (id, status, workflow, tags, timestamps, the structured `error`) is
left untouched:

```ts
import { CodecStateStore } from '@dudousxd/nestjs-durable-core';

const store = new CodecStateStore(new TypeOrmStateStore(dataSource), {
  encode: (value) => aesEncrypt(value),
  decode: (value) => aesDecrypt(value),
});

DurableModule.forRoot({ store, transport });
```

Both `encode`/`decode` are synchronous — wrap an async KMS call yourself if you need one. It's
adapter-agnostic, so it composes with any of the four stores.

## Retention & pruning

Terminal runs (`completed`, `failed`, `cancelled`, `dead`) otherwise accumulate forever. The
`retention` module option sweeps them on an interval, hard-deleting whatever falls outside your
policies:

```ts
DurableModule.forRoot({
  store,
  transport,
  retention: {
    sweepInterval: '1m',
    batchSize: 1_000,
    policies: [
      { statuses: ['completed', 'cancelled'], maxAge: '14d', maxCount: 200 },
      { statuses: ['failed'], maxAge: '90d' }, // keep failures longer for debugging
    ],
  },
});
```

Each `RetentionPolicy` targets a set of terminal statuses (disjoint per `scope` — a policy can be
confined to a namespace, tags, workflows or search attributes); a run is kept only while it
satisfies every bound you set on its status (`maxAge`, `maxCount`, or both — the most-restrictive
wins) and is pruned the moment it violates one. `sweepInterval: 0` runs the sweep once on boot only.
Pruning needs the store to implement `pruneTerminalRuns` — optional on `StateStore`, so a custom
store without it no-ops with a warning instead of failing boot. Every bundled adapter implements it,
along with the bulk `deleteRuns` behind `engine.purgeRuns` (see
[Retention](/docs/reliability/retention#purging-on-demand)).

<Callout type="warn">
  **`withScope` is MikroORM + Drizzle (Postgres) only.** Multi-tenant setups can turn on
  `scopeReads: true` (with `namespace` set) to confine the operator's own reads to one tenant. The
  module applies this by asking the store for a scoped view via an optional `withScope(scope)`
  capability — today only the MikroORM and Drizzle Postgres adapters implement it. Against TypeORM,
  Prisma or Drizzle (SQLite), `scopeReads` silently has no
  effect: the store keeps returning every namespace's runs. If you need tenant-scoped reads on one of
  those adapters, scope the query yourself rather than relying on `scopeReads`.
</Callout>
