Which [shape](/docs/cluster) a process takes is inferred from the options you give it. The
**`topology` preset** on `DurableModule.forRoot` lets you name the role instead, and validates the
two axes that otherwise read as synonyms — `namespace` (the operator's poll scope) versus `partition`
(a worker's queue suffix). `topology` is entirely additive: omit it and inference behaves exactly as
before.

## The configs

<Tabs items={['Single process', 'Control plane', 'Thin worker', 'Read replica']}>

<Tab value="Single process">

Omit `topology` and you get the default: an operator that owns the store and runs every `@Workflow`
on the inline fast path.

```ts
DurableModule.forRoot({
  store,
  transport: new EventEmitterTransport(),  // or BullMQ for cross-process
})
```

Add a `connection` and the same process keeps the store but moves execution onto a co-located BullMQ
consumer — every `@Workflow` becomes group-served instead of inline.

</Tab>

<Tab value="Control plane">

A coordinator: it owns the store and the transport, dispatches, recovers, fires timers, prunes
retention, and answers thin-pod requests.

```ts
DurableModule.forRoot({
  topology: { role: 'control-plane' },   // optional `tenant` scopes it to its own namespace
  store,
  transport,                             // BullMQ for a cross-process/polyglot fleet
  retention: { policies: [{ statuses: ['completed', 'cancelled'], maxAge: '14d' }] },
})
```

<Callout type="warn">
The preset does not switch execution off. Bodies run wherever their `@Workflow`/`@Step` providers are
registered — declare them here and this process starts consumers for them. Whether that actually
takes work from your workers depends on the partition: without `tenant` this node is on the bare
queue tokens and never sees a tenant's dispatches, while **with** `tenant` it deliberately subscribes
the same `<name>@<tenant>` tokens it dispatches to. See
[dispatch vs execution](/docs/cluster#dispatch-and-execution-are-separate).
</Callout>

</Tab>

<Tab value="Thin worker">

A store-less worker sets a `connection` (Redis) and **no `store`** — that is what makes it
store-less. It consumes its partition's queues, executes the `@Workflow`/`@Step` bodies registered in
the module, and publishes results. The NestJS process **is** the worker: the module starts the
consumer on bootstrap, with no separate CLI.

```ts
DurableModule.forRoot({
  topology: { role: 'tenant', tenant: 'acme-corp' },  // maps to the partition it serves
  connection: process.env.REDIS_URL,                  // Redis — no `store`
})
```

A store-less **api/dashboard pod** is the same config in an HTTP app that registers no handlers: it
executes nothing and proxies every read and control action to the control plane.

</Tab>

<Tab value="Read replica">

An operator that mounts the store and the dashboard for reads but runs none of the driving loops.

```ts
DurableModule.forRoot({
  store,
  transport,
  drive: false,   // no poll, recovery, timers, timeout sweep, retention or local step consumption
})
```

<Callout type="warn">
`drive: false` is not "a lighter control plane" — nothing ticks on it. A driving operator must be
running somewhere or pending runs never start, crashed runs never recover, and timers never fire.
</Callout>

</Tab>

</Tabs>

<Callout>
Any role that sets `connection` executes bodies through `@dudousxd/durable-worker`, which is an
**optional** peer — `pnpm add @dudousxd/durable-worker bullmq ioredis` alongside the module. An
operator that only owns a `store` never loads it and does not need it installed.
</Callout>

## What `topology` validates

Each check is named after the axis it protects, and runs at `forRoot`/`forRootAsync` resolution time:

| `topology` | Requires | Forbids | Notes |
| --- | --- | --- | --- |
| `{ role: 'control-plane', tenant? }` | `store` **and** (`transport` or `transports`) | `partition` | `tenant` is optional and maps onto `namespace`. Omit it on a deployed operator (it then drives every tenant); set it to scope a self-contained local stack to its own runs while sharing a broker with a deployed cluster. Setting `namespace` too is allowed only when it equals `tenant`; a mismatch throws. |
| `{ role: 'tenant', tenant }` | `connection` | `store`, `namespace` | `tenant` is required and maps onto `partition`. Setting `partition` too is allowed only when it equals `tenant`; a mismatch throws. |

The preset exists for the case plain inference can't catch: an app that sets both `namespace` (meant
for the operator) and `partition` (meant for a worker) on one instance because the two options read
as near-synonyms. `topology` forces you to pick one role and rejects the other role's axis outright,
with an error message that explains why. What each axis actually partitions is
[Tenancy](/docs/concepts/tenancy).

## The shared surface: `RunGateway`

Every shape binds exactly one `RunGateway`, and the role picks the implementation. An operator with a
`store` reads its store directly (`StoreRunGateway`). A store-less pod binds a `ProxyRunGateway` that
round-trips every call over the transport to the control plane, which reads *its* store and answers.

**This is what makes application code portable across shapes.** Your controllers and the
[dashboard](/docs/observability/dashboard) call the same interface either way, so a pod moving from
single-process to store-less changes only its `forRoot` — no controller code, and the identical
`DurableDashboardModule` mounts on both.

```ts
@Controller('runs')
export class RunsController {
  constructor(private readonly gateway: RunGateway) {}   // inject by type — the class is its own token

  @Get(':id')
  async show(@Param('id') id: string) {
    return (await this.gateway.getRunDetail(id)) ?? {};
  }
}
```

| Verb | Purpose |
| --- | --- |
| `topology()` | this pod's role, plus its `tenant` when store-less. Synchronous — no round-trip. |
| `getRunDetail(runId, options?)` | one run plus its step timeline and child ids, or `null`. With `{ summarizeFansOver: n }`, every fan wider than `n` comes back as a `FanSummary` in `fans` instead of its members, and `children` is capped at 200 with `childCount` as the total. Unset returns the full detail. |
| `getFanMembers?(runId, group, query)` | *optional* — one page `{ items, total }` of a fan's members; `query` is `{ offset?, limit?, failedOnly? }` (limit defaults to 100, at most 500) |
| `getRun?(runId)` | *optional* — the run alone, without its timeline |
| `listRuns(query)` | a filtered listing (status, workflow, tag, namespace, search attributes), each row optionally carrying what a suspended run is parked on |
| `runFacets(query)` | whole-set counts grouped by `(status, origin)` — exact even when the listing is paginated |
| `runValueFacets(axis, query, opts?)` | the distinct values of one filter axis (tag, tenant, origin, workflow, search-attribute key or value) with counts — what fills a console's pickers |
| `waitingFor(runIds)` | bulk-resolve what each of an arbitrary set of runs is parked on |
| `workerHealth()` | queue backlog and live worker heartbeats per group; scoped to the requester's own groups over a tenant proxy |
| `cancel(runId, opts?)` | cancel a run, with `{ compensate: true }` to run its [saga undo](/docs/reliability/sagas) first |
| `retry(runId)` / `continue(runId)` | re-drive a failed run, or push a dead one one step further |
| `retryWithInput(runId, input)` | fix-and-replay: a fresh run from corrected input, keeping the original's namespace |
| `redispatchPending(runId)` | re-enqueue every remote step still `pending` — the operator escape hatch for a lost dispatch |
| `subscribe(runId, onEvent)` | live-tail one run's lifecycle events; returns the unsubscribe |

Tune the proxy round-trip with `runGatewayTimeoutMs` (default `10_000`). It is ignored on an
operator, which is bound to the store-backed gateway.

### Wide fans over the gateway

The dashboard asks `getRunDetail(id, { summarizeFansOver: 50 })` and pages a fan with
`getFanMembers` (see [Wide fans](/docs/observability/dashboard#wide-fans)). `StoreRunGateway`
implements both, plus `getRun`. On a store-less pod, `ProxyRunGateway` forwards the detail options
in its `getRunDetail` request and sends `getFanMembers` and `getRun` request kinds. `getRun` answers
the run alone, so a caller that only needs a run's status (a cancel check, say) does not ship the
whole timeline over the wire. The control plane's
responder checks that the requesting tenant owns the run before it pages the fan, as it does
before every run-scoped verb, so a tenant cannot page another tenant's fan. A control plane older
than the tenant still serves both. See [Rolling upgrades](#rolling-upgrades).

If you implement `RunGateway` yourself:

- **`summarizeFansOver`** is a hint. A gateway that ignores it returns the full detail, and the
  console renders every member as before.
- **`getFanMembers`** is optional. Without it, the dashboard's `GET runs/:id/fans/:group` answers
  404, so a summarized fan can be drawn but not expanded. Core exports `summarizeTimeline`,
  `summarizeFan`, `pageFan` and `childIdsOf`, so a gateway that already loads the checkpoints can
  implement both in a few lines, the way `StoreRunGateway` does.
- **`getRun`** is optional. The ownership check uses it to read only the run row; without it, the
  check falls back to `getRunDetail`, which reads every checkpoint of the run.

<Callout type="info">
**`cancel` on a store-less pod: same verb, two objects, opposite answers.** Injecting
`WorkflowEngine` there gets you a **start-only** client — `start` publishes a start message over the
wire, but `cancel`, `deleteRun`, `resume`, `signal`, `signalWithStart` and `publishEvent` reject with
a named `tenantUnsupported(...)` error, because they reach for a store the pod does not have. The
`RunGateway` above has no such problem: its `cancel` is a wire request the control plane answers
against *its* store, so it works on every shape.

That is why the table lists `cancel` as a working verb. It is `RunGateway.cancel` that works;
`WorkflowEngine.cancel` is the one that rejects. Inject `RunGateway` in anything that has to run on
more than one shape, and you never meet the distinction.
</Callout>

### Rolling upgrades

Tenant pods and the control plane can be upgraded in either order. While they are on different
releases, run detail keeps working in both directions:

| Tenant | Control plane | What happens |
| --- | --- | --- |
| 0.47.2+ | 0.46.x or older | The old responder ignores the detail options and has no `getFanMembers`. `ProxyRunGateway` sees the full detail come back without `fans` and summarizes it on the tenant. A `getFanMembers` gets no data from an old responder, so the proxy reads the full detail and pages the fan out of it. Both fallbacks happen on that reply, with no timeout wait. A `getRun` gets no data either, so the proxy takes the run out of the full detail. |
| 0.47.0 or 0.47.1 | 0.46.x or older | These tenants have no fallback: run detail comes back unsummarized and fan pages answer 404. Upgrade the control plane first, or move the tenants straight to 0.47.2. |
| 0.46.x or older | 0.47.0+ | An old proxy never sends detail options or `getFanMembers`. The new responder answers its requests exactly as before: a full detail, and the same ownership checks. |

After a control plane answers that it does not know `getFanMembers` (or `getRun`), the proxy pages fans locally
for the next minute before it asks again. The control plane can be several pods behind one queue,
mid-upgrade themselves, and a reply does not say which pod sent it. So the proxy treats the whole
control plane as old until that minute is up. The result is the same either way. Only the cost
changes: the old path moves every checkpoint of the run over the wire, so on a run with a very wide
fan, finish upgrading the control plane soon.

From 0.47.2 on, a responder answers a request kind it does not know with an error whose `code` is
`unsupported-request`, without touching the store. The next new verb can fall back the same way on a
control plane that does not have it. A responder whose gateway throws replies with that error, so a
tenant no longer waits out `runGatewayTimeoutMs` for an answer that will never come.

## Layered tenant authentication

The `tenant` on a wire request is a **claim**. Without authentication the
[isolation boundary](/docs/concepts/tenancy#the-isolation-boundary) is meaningless — any pod could
ask for any tenant's runs. Durable stacks **two** layers:

<Steps>

<Step>

### Prefix / network baseline

Each tenant runs on a segmented transport prefix/namespace behind a Redis/network ACL, so a pod can
only reach its own prefix. No application code.

</Step>

<Step>

### Signed token on top

Each tenant pod carries a secret-signed token. The control plane **verifies the signature and derives
the tenant from the token**, ignoring any `tenant` in the request body — defense in depth.

</Step>

</Steps>

Both sides are optional and off by default. Turn the second layer on with `verifyTenant` on the
control plane and `tenantToken` on each tenant pod:

```ts
import { hmacTenantVerifier, signTenantToken } from '@dudousxd/nestjs-durable';

// Mint the token a tenant pod presents (once, e.g. in your provisioning script). The pod carries
// only the token, never the secret. `ttlMs` makes it expire, so a captured token stops replaying:
const token = signTenantToken('acme-corp', process.env.DURABLE_TENANT_SECRET!, { ttlMs: 86_400_000 });

// Control plane: verify it. A secret LIST makes rotation a two-step deploy — verify with
// [next, current] first, then re-mint tokens with `next` at leisure.
DurableModule.forRoot({
  topology: { role: 'control-plane' },
  store,
  transport,
  verifyTenant: hmacTenantVerifier([process.env.DURABLE_TENANT_SECRET_NEXT!, process.env.DURABLE_TENANT_SECRET!]),
});

// Tenant pod: present it. A function is called before every request, so a short-lived token can be
// re-minted or fetched from a secret store without a restart.
DurableModule.forRoot({
  topology: { role: 'tenant', tenant: 'acme-corp' },
  connection: process.env.REDIS_URL,
  tenantToken: process.env.DURABLE_TENANT_TOKEN!,   // or: () => fetchTenantToken()
});
```

A token provider runs before the request is sent, and the request's timeout starts only once it has
resolved: the deadline covers the control plane's round trip, not the provider. A provider that rejects
fails the request.

The token travels **in the existing `tenant` field** of every `RunRequest` and `StartRunMessage`, so
the wire shape does not change. It is `<claim>.<base64url(HMAC-SHA256(secret, claim))>`, where the
claim is the tenant name, optionally followed by `.exp<epochMs>` when minted with `ttlMs`. The live-tail
channel stays keyed by the partition, never the token.

With a verifier configured, the control plane:

- answers a run request whose token is missing, tampered, expired or signed with another secret with
  `{ ok: false, error: { message: 'invalid or unauthorized tenant token', code: 'unauthorized' } }`,
  before any run is touched. `ProxyRunGateway` rejects with a `RunGatewayError` whose `code` is
  `unauthorized` (`cross-tenant` for a run owned by another tenant), so `err.code` is typed;
- drops such a start-run without creating a run (logged; the start channel has no reply);
- scopes every accepted request to the tenant **derived from the token**, never the wire claim;
- turns a verifier that throws into an error reply, so the tenant never waits out its timeout.

Bring your own verifier for asymmetric or issued tokens: `verifyTenant` is any
`({ token, tenant }) => { tenant, capabilities? } | null` (sync or async). `capabilities` is carried
on the verified identity but **not enforced yet**: a verified tenant can call every verb, scoped to its
own namespace.

Without `verifyTenant` the wire `tenant` is trusted **verbatim** — any process with broker access can
list, cancel and start runs as any tenant (prefix/network isolation only). An explicit
`topology: { role: 'control-plane' }` without a verifier therefore logs a warning when its responder
starts. A plain operator (no `topology`, role inferred from `store`) boots silently, because an app
that never serves tenants has nothing to protect there.

The scheme is byte-compatible with Agora (`@adonis-agora/durable`): a token minted by either side
verifies on the other, and the `unauthorized` reply is identical. See
[interop](/docs/cluster/interop#tenant-tokens-across-runtimes).

The control plane is the **trust boundary** for these proxied requests: it forces `listRuns` to the
requester's own tenant (no cross-tenant enumeration), validates `run.namespace === tenant` on every
runId-bearing verb (anti-IDOR), and rejects unknown verbs and tampered tokens.
