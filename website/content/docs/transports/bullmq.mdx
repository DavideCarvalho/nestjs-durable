`@dudousxd/nestjs-durable-transport-bullmq` carries steps over BullMQ/Redis — the path for steps
that run in another process or another language (e.g. a [Python worker](/docs/python)).

```bash
pnpm add @dudousxd/nestjs-durable-transport-bullmq bullmq
```

How it compares to the other transports: see [Choosing a transport](/docs/transports/choosing).

## How it works

- `ctx.step` dispatches a task to a **per-name** queue: `<prefix>-tasks-<name>[@<partition>]`.
- A worker registered for that step name consumes it, runs the handler, and adds the result to the
  shared `<prefix>-results` queue.
- The engine-side instance consumes results and checkpoints them.

Run **one instance engine-side** (consumes results) and **one per worker process** (registers its
handlers, and dispatches on the transport):

```ts title="engine side (your NestJS app)"
const transport = new BullMQTransport({ connection: { host: 'localhost', port: 6379 } });

DurableModule.forRoot({ store, transport });
```

```ts title="worker side (a separate process)"
const transport = new BullMQTransport({
  connection: { host: 'localhost', port: 6379 },
  partition: 'payments', // optional isolation suffix — omit for a single-tenant deployment
});
transport.handle('payments.charge-card', async (input) => ({ chargeId: await charge(input) }));
```

## Concurrency

`concurrency` controls how many tasks this instance runs at once from each of its per-name task
queues (the BullMQ `Worker`'s own concurrency). It takes three forms:

- a fixed number — always runs exactly that many in parallel. Defaults to `1` (one task at a time).
- `'adaptive'` — an `AdaptiveController` self-tunes the limit from a latency gradient, a RAM brake,
  and backpressure (errors/stalls), instead of you guessing a number.
- `{ mode: 'adaptive', ... }` — adaptive with overrides (`min`, `max`, `start`, `ramCeilingPct`,
  `cpuCeilingPct`, `tickMs`). The defaults are `min: 1`, `max: 32`, `start: min`,
  `ramCeilingPct: 85`, no CPU ceiling, and `tickMs: 2000`. To pin the limit instead, pass a plain
  number.

A number that is not finite or is out of range falls back to its default: a fixed value, `min`,
`max`, `start` or `tickMs` below 1 (or `NaN`, `Infinity`) uses the default, and so does a
`ramCeilingPct` of 0 or less. A bad `cpuCeilingPct` turns the CPU ceiling off. A fractional count
is rounded down.

Watch an adaptive worker breathe — spike the load and it grows into its headroom; fire the RAM
brake and it backs off before memory melts:

<AdaptiveSim />

```ts
const transport = new BullMQTransport({
  connection: { host: 'localhost', port: 6379 },
  concurrency: { mode: 'adaptive', min: 2, max: 32, ramCeilingPct: 85 },
});
```

Total parallelism across a fleet is `concurrency × replicas`. Only adaptive mode runs a control
loop; a fixed limit never moves and runs no timer. Either mode publishes its live status — current
limit, in-flight count, RSS, CPU, throughput, p95 and (adaptive) the last adjustment — on the
worker's heartbeat as a `WorkerStatus`. Throughput is completions per minute over the trailing
minute, so an idle worker's reading decays and drops to 0 once a minute passes with no completion. See [Flow control](/docs/reliability/flow-control#worker--transport-concurrency)
for the full set of tunables and how the Telescope Workers dashboard renders it.

### Result concurrency

`concurrency` governs the **task** queues a worker consumes. The engine side consumes the shared
`<prefix>-results` queue, and `resultConcurrency` sets how many results this instance handles at
once. It defaults to `1`.

Each result settles its step's checkpoint and then resumes the run inline. With one result at a time,
a pod drives one run turn at a time off results, so the results of a wide fan queue up behind it.
Raise `resultConcurrency` on the instances that consume results:

```ts
const transport = new BullMQTransport({
  connection: { host: 'localhost', port: 6379 },
  resultConcurrency: 16, // results of different runs handled in parallel
});
```

Results of the **same** run still resume it in order on an instance. They are settled in batches:
the results of a run that arrive while one batch is being written go into the next, which claims
their checkpoints with one `saveCheckpointsIfPending` call and checks a step fan's join barrier once.
A batch resumes the run at most once, and each result is acknowledged only after its batch commits.
The turn a batch triggers waits for the previous turn of that run on this instance. A run never gets
two concurrent turns from one instance, and different runs proceed in parallel. The engine applies the same ordering to any
transport that delivers results concurrently, including the in-process ones.

A value that is not a finite number of at least 1 (`NaN`, `Infinity`, `0`) falls back to the default
of `1`; a fractional value is rounded down.

### Result delivery

A result job whose handler throws (a store error at peak load, say) is retried up to 5 times with
exponential backoff starting at 500 ms. A result that still fails is kept in the results queue for
24 hours instead of being removed, and the transport logs that it gave up on it, with the step and
run ids.

## Priority

Per-call `priority` on `ctx.step` follows the engine's convention: **higher wins**. BullMQ's own job
priority is the opposite — lower numbers run first — so the transport translates one into the other
before enqueuing, keeping "higher = more urgent" true end-to-end regardless of transport. Leave
`priority` unset for the default FIFO ordering.

## Namespace

`namespace` segments every queue/stream/key this instance touches, so a single Redis can host
several isolated deployments — e.g. one per developer — without crosstalk. Leave it unset (or
`"default"`) for production: names stay byte-identical to the un-namespaced scheme. Any other value
inserts a `-<namespace>` segment into every name. See [Tenancy](/docs/concepts/tenancy) for the
operator/tenant model this enables.

## Run queue

The engine queues the runs it starts or wakes on `<prefix>-runs` (`<prefix>-runs-<namespace>` for an
engine scoped to a namespace), and every driving instance consumes it, 256 at once. A start's job id
is `start-<runId>-<key>` (`:` escaped as `%3A`), where the key names the `pending` state it is for:
a start re-sent for that state is not queued twice, and a run that went `pending` again is a new
job even while the earlier one is being handled. A wake has no job id, so none is dropped. A fan's
children go in `addBulk` writes of up to 500, and a run's `priority` maps onto the job's as for a
step. A job held by an instance that went down is redelivered by BullMQ's stalled check. The job ids
are the same as adonis-agora-durable's.

## Crash recovery

A worker that crashes or stalls mid-step never produces a `StepResult`, so without help the step's
checkpoint would stay `pending` forever. `BullMQTransport` closes that gap **automatically**:
BullMQ's own stalled-check (run by a peer worker's `Worker`) marks a crashed/stalled task job
`failed`, and a `Worker.on('failed')` listener bridges that into a synthetic failed `StepResult` —
so the engine settles the checkpoint as `failed` and its normal durable retry re-dispatches the
step. A handler business error is unaffected: `runStepHandler` already turns it into a
*successful* job carrying a failed `StepResult`, so there's no double-publish.

No configuration needed on your part — `dispatch()` sets `removeOnFail: { age: 24h }` on every
task job (overriding the default immediate `removeOnFail`) so a failed job's payload survives long
enough for the bridge to read the `runId`/`seq`/`stepId` it needs, before BullMQ garbage-collects
it.

**The bridge lives in the consumer, not the queue.** A worker in another language consumes the
same queues, and the bridge only exists where somebody implemented it: the TypeScript transport
here, and the Python `durable-worker` (from the release that ships its own `failed` listener —
earlier versions had none, so a Python fleet's steps orphaned where a Node fleet's did not). If
you run a worker on an SDK without it, treat the checkpoint as unsettled and rely on the engine's
`remoteRedispatchMs` self-heal below.

Residual gaps, both of which the engine's opt-in `remoteRedispatchMs` self-heal covers (see
[Retries](/docs/reliability/retries#a-third-case-the-dispatch-itself-gets-lost)):

- if the **only** worker for a queue crashes and never restarts, no peer's stalled-check ever
  runs, so nothing settles the checkpoint;
- if the consuming SDK has no failure bridge, the job's terminal failure is never turned into a
  result.

See also [Recovering a lost remote step dispatch](/docs/observability/dashboard#recovering-a-lost-remote-step-dispatch).

## Producer-only processes

A BullMQ `Worker` starts fetching the moment it is created, and the task, results, decisions,
step-events, start-run and run-request queues each hand a job to ONE consumer. A process that boots
the module without being a worker — a CLI command, a REPL, a migration or seed script — would
compete with the real fleet: it claims jobs it then dies holding, and takes results meant for the
long-lived engines. Make it a pure producer:

```ts
DurableModule.forRoot({ store, transport, drive: false, consumers: false });
```

`consumers: false` calls `transport.deferConsumers()` before the engine subscribes, and starts no
co-located or thin worker consumer. The process still dispatches and starts runs; the jobs wait on
the queues for the fleet, and it is not advertised as a live worker. `transport.startConsumers()`
starts the parked consumers later, if the process turns out to be a worker after all. Outside the
module, construct the transport with `deferConsumers: true` (or call `deferConsumers()` before any
`handle()` / `onResult()`). Pub/sub (heartbeats, control, run replies, tenant events) is broadcast
and is not parked.

## Control plane & tenant protocol

Every `onDecision` and `onResult` handler registered on one transport gets every decision and every
result, over a single consumer each. Two engines sharing a transport is safe: an engine settles a
result by claiming the step's still-pending checkpoint, so an engine that doesn't know the run does
nothing, and over one store only one engine wins the claim.

Beyond `Transport`, `BullMQTransport` also implements `ControlPlane` — cross-instance broadcast for
lifecycle events and cancellation — and carries the tenant `start-run` / `run-request` / `run-reply`
/ tenant-event protocol a store-less tenant worker uses to proxy runs through an operator. See
[Tenancy](/docs/concepts/tenancy) for the full model.

## Options

| Option | Description |
| --- | --- |
| `connection` | ioredis connection options, an `IORedis` instance, or a `redis://` / `rediss://` URL (host, port, credentials, db and TLS are read from it; query parameters are refused). |
| `deferConsumers` | Start with every point-to-point consumer parked until `startConsumers()`. See [Producer-only processes](#producer-only-processes). Defaults to `false`. |
| `partition` | Optional isolation suffix appended to every one of this instance's per-name queues (`<name>@<partition>`). Omit for a single-tenant deployment. |
| `prefix` | Namespaces the queues. Defaults to `durable`. |
| `namespace` | Logical deployment namespace segmenting every queue/stream/key. See [Namespace](#namespace) above. |
| `instanceId` | Stable id for this worker process, stamped into its heartbeats/liveness keys. Defaults to `ts-<hostname>-<pid>`. |
| `concurrency` | Fixed number, `'adaptive'`, or `{ mode: 'adaptive', ... }`. See [Concurrency](#concurrency) above. Defaults to `1`. |
| `resultConcurrency` | How many step results this instance handles at once from the results queue. One run's results still resume it in order. See [Result concurrency](#result-concurrency). Defaults to `1`. |

The payload is the documented `RemoteTask` / `StepResult` JSON, so a non-Node worker on the same
queues interoperates — that's exactly how the [Python worker](/docs/python) plugs in.
