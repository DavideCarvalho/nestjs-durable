Workflow code on a `DurableModule` tenant (or any TypeScript thin worker) now runs like it does on a standalone engine. A step's `retries`, `backoff`, `backoffMs`, `backoffMaxMs`, `jitter` and `timeoutMs` (from `@Step({ ... })` or the `ctx.step` options) ride the remote `call` decision as its `policy`, and the control plane enforces them with the in-process rules: a failed attempt is dispatched again after its backoff unless the handler marked it non-retryable, and a `timeoutMs` attempt that returns nothing in time is dispatched again, then fails with `error.code: 'remote_step_timeout'`. `ctx.sleepUntil`, `ctx.waitForSignal(token, { timeoutMs })` (throws `SignalTimeoutError`), `ctx.waitForEvent(name, { match, timeoutMs })`, fire-and-forget `ctx.startChild` (`childId`, `priority`), `ctx.continueAsNew` and `ctx.setEvent` work on the thin worker, through the new `sleepUntil`, `waitSignalTimeout`, `waitEvent`, `spawnChild` and `continueAsNew` decisions. The control plane advertises the decisions it applies on each workflow task (`WorkflowTask.features`, `REMOTE_WORKFLOW_FEATURES`); a worker whose control plane is older fails the turn with `UnsupportedByControlPlane` (`error.code: 'control_plane_unsupported'`) instead of sending a command that would be rejected or ignored, so upgrade the control plane first. An older worker keeps working against a newer control plane. `ctx.patched`, `ctx.upsertSearchAttributes`, `ctx.waitForRun`, `startChild` with `version` or `parentClose`, and the other engine-only ops still throw `UnsupportedOnThinWorker` naming the op. The worker's peer range on core is now `>=0.103.0`.
