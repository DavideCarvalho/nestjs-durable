`@Workflow({ input })` types and feeds the `singleton` and `concurrency` keys from the input schema.

- **Typed keys.** `Workflow` and `WorkflowOptions` are generic over the `input` schema. With one, `singleton.key`, `concurrency.key` and `validateInput` take the schema's parsed type (`StandardSchemaV1.InferOutput`, `z.output`, or a DTO class's instance), so `key: (input) => \`company:${input.companyId}\`` needs no cast and a wrong property is a compile error. Without a schema they take `unknown`, as before, and `WorkflowOptions` written without a type argument (an annotation, an interface extending it) still accepts any `input`. `SingletonConfig<TInput>` and `ConcurrencyConfig<TInput>` gain a type parameter that defaults to `unknown`. The new `InferWorkflowInput<typeof Schema>` types `run(ctx, input)` from the same schema.
- **The keys receive the parsed input.** They used to receive the input as sent, while `run` got the parsed value. Now, with an `input` schema, every path that evaluates a key hands it the parsed value: a local start, a schedule, each turn's singleton admission (including a requeued run), a tenant start and a tenant's announced schedule. `start` parses the input once: a parse failure rejects it (a tenant start records it as rejected), and `validateInput` and both keys read that one parsed value. Each turn's admission parses the stored input again and claims under that exact key. A turn whose stored input no longer parses runs without a slot, and the body fails it with `invalid_input` before any of its code runs. The run still stores the input as sent. In core this is the new `register(..., { parseInput })` option (with it, `validateInput` receives the parsed value); without it nothing changes.
- **Upgrade window.** If the schema transforms or coerces (`.transform()`, `z.coerce.*`, a DTO instance), a run queued before the upgrade keeps the key computed from its raw input, while a new start of the same entity can get a different, parsed key. Until the older runs drain, both can hold a slot. Drain the backlog of such a singleton workflow before upgrading if that matters. An older run still waiting is admitted under the tag it was stamped with, which the engine recomputes the old way, from the stored input as sent: a key that relies on parsed-only fields should tolerate that shape until those runs are gone, or the run keeps waiting.
- **`singleton:` tags are the engine's.** A `singleton:` tag passed in a start's `tags`, a workflow's static `tags` or a tenant start-run is now dropped, so a caller tag can no longer make a run queue or be admitted under a key its input does not have; `retryWithInput` re-derives the key from the new input instead of carrying the old one.
- A run that carries no `singleton:` tag (one started before its workflow became a singleton) is still not admitted, as before this release.
- The `debounce`/`batch` `key` of `@OnWorkflowCompleted` / `@OnWorkflowFailed` is unchanged: it is typed from the subscription's `input` mapping and receives what that mapping builds.
- `@dudousxd/nestjs-durable` now needs `@dudousxd/nestjs-durable-core` >= 0.104.0.
